# Xray Studio

[English](README.md) · **Русский**

Десктопный инструмент для тестирования конфигураций Xray-core: показывает, **почему**
балансировщик выбрал конкретный outbound, и позволяет сделать отдельные outbounds
недоступными так, что это неотличимо от настоящего сетевого отказа.

Собран против **Xray-core v26.7.28**.

> **Альфа.** Интерфейсы и форматы файлов могут поменяться без предупреждения. И важнее
> того: инъекция сбоев действует на **настоящие серверы из открытого вами конфига** —
> песочницы или лабораторного режима нет намеренно, потому что смоделированный отказ
> ничего не доказал бы про вашу реальную схему. Не направляйте его на продакшн, который
> нельзя потревожить.

> **Интерфейс приложения английский.** Переводится только документация по параметрам —
> её публикует апстрим Xray, и переключатель для неё стоит в шапке с подписью `docs`.

![Воронка решения](docs/img/funnel.png)

<sup>Каждый этап настоящего решения `leastLoad`: кандидаты, арифметика, кто отсеян и
почему — и бросок кубика в конце, названный броском кубика.</sup>

## Установка

Скачайте из [Releases](../../releases). По одному файлу на систему:

| система | файл | как |
|---|---|---|
| **macOS** 14+ | `macos-universal.dmg` | открыть, перетащить в Applications. Intel и Apple Silicon в одной сборке |
| **Windows** 10+ | `win-x64.zip` | **портативная** — распаковать куда угодно, запустить `Xray Studio.exe`. Брать нужно эту |
| **Windows** 11 ARM | `win-arm64.zip` | опционально. Имеет смысл только ради нативной скорости на машине со Snapdragon — сборка x64 там тоже работает, под эмуляцией |
| **Arch Linux** x86_64 | `linux-x86_64.pkg.tar.zst` | `sudo pacman -U <файл>` |
| **Arch Linux** ARM | `linux-aarch64.pkg.tar.zst` | `sudo pacman -U <файл>` |

Если взять не тот файл для Windows, она скажет *«This app can't run on your PC»* — это
сообщение всегда означает несовпадение архитектуры и никогда не означает битую загрузку.
`win-x64.zip` — безопасный выбор: на обычных ПК работает нативно, на Windows 11 ARM под
эмуляцией. Берите `win-arm64.zip`, только если точно знаете, что машина ARM, и хотите
нативной скорости; если не уверены, `$env:PROCESSOR_ARCHITECTURE` в PowerShell напечатает
`AMD64` или `ARM64`.

**Под Windows нет установщика.** За пределы папки ничего не пишется: ни ключей реестра,
ни записи об удалении, ни `%APPDATA%`. Настройки — API-ключ, профиль окна, вставленные
конфиги — лежат в `XrayStudio-data` рядом с исполняемым файлом, поэтому удаление папки
убирает все следы, а копирование её на флешку переносит вашу настройку с собой. Если
положить папку туда, где нет прав на запись, например в Program Files, приложение
откатится на `%APPDATA%`, а не откажется запускаться.

Одна вещь между машинами не переезжает: API-ключ шифруется через Windows DPAPI и привязан
к учётной записи, которая его сохранила. Папка на другой машине откроется, но ключ
придётся ввести заново.

Windows и Linux требуют по два файла, и по одной причине: универсального формата
бинарника на Linux не существует — ни fat binary, ни аналога, — поэтому пакет собирается
под одну архитектуру или под другую. Имена в точности такие, какие печатает `uname -m`,
так что запустите его, если не уверены.

AppImage — то, за чем стоит тянуться, когда зависимости не хватает или она не той версии:
он вообще не разрешает пакеты, поэтому не может сломаться так, как ломается установка.
Полностью самодостаточным он при этом не является: Electron и его приватные библиотеки
едут внутри, но `gtk3`, `nss` и `glibc` по-прежнему берутся у хоста. Убрать эту последнюю
зависимость могли бы только Flatpak или контейнер, а здесь не собирается ни то, ни другое.

Если он отказывается стартовать с ошибкой FUSE, запустите как
`./XrayStudio-*.AppImage --appimage-extract-and-run`.

Пакет для Arch ставится в `/opt` вместе с ярлыком и иконками. Его зависимости выведены из
собственных записей `DT_NEEDED` поставляемого бинарника, а не скопированы из шаблонного
списка для Electron — `gtk3`, `nss`, `alsa-lib`, `libcups`, `mesa`, `systemd-libs`,
`dbus`, `at-spi2-core`, `xdg-utils`, — поэтому `pacman` подтянет ровно то, чего не
хватает, и ничего из того, что убрали из репозиториев годы назад.

Что ещё лежит в релизе:

| файл | что это |
|---|---|
| `src.tar.gz` | исходники, из которых собран этот релиз, прямо из `git archive` на теге |
| `*.blockmap` | не для скачивания — карта блоков переменной длины и их хешей, по которой будущий автообновлятор скачает только изменившиеся части установщика вместо всех 200 МБ |

Ни одна из сборок не подписана. На macOS нужно один раз снять карантинный флаг, а Windows
предупредит о неизвестном издателе:

```bash
xattr -dr com.apple.quarantine "/Applications/Xray Studio.app"
```

Про сборку из исходников — в разделе [Как начать](#как-начать).

## Зачем это нужно

Ничего из того, как рассуждает балансировщик, из собственного API Xray получить нельзя:

- `RoutingService.GetBalancerInfo` возвращает только `{override, principle_target}` — ни
  стратегии, ни кандидатов, ни оценок, ни причин отсева. Для `random` и `roundRobin` он
  возвращает *сырой нефильтрованный* вывод селектора; для `leastPing` — один тег; и
  только для `leastLoad` — ранжированный список, да и то уже после усечения и без оценок.
- `SubscribeRoutingStats` — мёртвый код: `app/router/command/command.go` всегда передаёт
  `nil` вместо канала статистики, поэтому RPC вечно отвечает
  `"Routing statistics not enabled."`, и конфигом это не включается.
- События начала и конца пробы, отдельные замеры RTT и совпадения правил по каждому
  соединению наружу не выставлены вообще.
- Когда стратегия не вернула ничего, а `fallbackTag` не задан, диспетчер молча
  маршрутизирует в **первый outbound в конфиге** и выбрасывает текст ошибки.

Поэтому ядро патчится — минимально, аддитивно и воспроизводимо, — чтобы выдавать
недостающее.

## Как начать

Нужны **Go ≥ 1.26**, **Node ≥ 22**, **git** и сеть при первом запуске (чекаут Xray-core
клонируется, а не вендорится). Разрабатывается на macOS arm64; слой errno у диалера сбоев
спрятан за build-тег, и пока существует только `_unix`, поэтому под Windows сборки ещё не
будет.

```bash
scripts/dev.sh
```

Эта команда клонирует Xray-core на запиненном коммите, накатывает серию патчей, собирает
сайдкар, ставит зависимости приложения и открывает окно. Примерно минута на холодную,
секунды на тёплую.

Если шаг клонирования падает на `git am`, почти всегда дело в подписи коммитов —
bootstrap отключает её внутри чекаута, но `gpg.program`, который запрашивает ввод, всё
равно может подвиснуть.

Дальше **Open config…**, выберите конфиг Xray и нажмите **Start**. Чтобы не открывать
диалог каждый раз:

```bash
XRAYSTUDIO_CONFIG=/путь/к/config.json scripts/dev.sh
```

Что делает каждая вкладка и как она выглядит — в **[экскурсии](docs/TOUR.ru.md)**. Здесь
уместны две вещи, которые относятся к сборке, а не к использованию.

Вкладка **Reference** и подсказки `?` генерируются из запиненного коммита
XTLS/Xray-docs-next — запинено по той же причине, что и ядро: незапиненный апстримный
текст молча менял бы то, что приложение говорит вам про ваш конфиг. Апстрим публикует
русский перевод тех же страниц, поэтому собираются оба бандла, а переключатель в шапке
выбирает между ними:

```bash
go -C tools run ./docsgen -out ../data/docs-en
go -C tools run ./docsgen -lang ru -out ../data/docs-ru
```

Вкладке **Protocols** нужна схема, восстановленная из запиненных исходников разбором
литералов реестра через `go/ast` — исходник единственное место, где записано, что
`"vless"` означает `VLessOutboundConfig`:

```bash
go -C tools run ./schemagen -src ../.build/xray-core/infra/conf -out ../data/schema
```

[`examples/demo-leastload.json`](examples/demo-leastload.json) — рабочая точка входа:
четыре outbound, балансировщик `leastLoad` с `expected: 2` и observatory, пробующая
`cp.cloudflare.com`. Откройте вкладку **Faults**, наведите чёрную дыру на один из тегов
`proxy-*` и смотрите, как observatory это замечает, а балансировщик переключается —
воронка во вкладке **Observe** назовёт причину.

```bash
scripts/test.sh
```

### Переменные окружения для разработки

| | |
|---|---|
| `XRAYSTUDIO_CONFIG=<путь>` | открыть и запустить конфиг при старте |
| `XRAYSTUDIO_TRACE=<путь>` | дописывать диагностику главного процесса (жизненный цикл окна, порт и токен сайдкара) в файл — stdout главного процесса Electron надёжно не перехватывается при отсоединённом запуске, из-за чего «окно не появилось» иначе недиагностируемо |
| `XRAYSTUDIO_SHOT=<png>[,<мс>]` | снять окно изнутри приложения, минуя разрешение macOS на запись экрана |
| `XRAYSTUDIO_SHOT_JS=<js>` | выполнить JS в рендерере перед снимком (выбрать вкладку, прокрутить) |
| `XRAYSTUDIO_SHOTS=<json>` | снять целую последовательность за один запуск и выйти — `[{file, js?, delay?}, …]`. Так `scripts/screenshots.sh` пересобирает набор для документации |

## Как это устроено

**Пропатченное ядро** (`xray/patches/`, 9 коммитов, ~380 строк в 12 файлах) добавляет
пакет `xraytrace` с тремя хуками, по умолчанию nil: события проб, решения балансировщика,
совпадения правил маршрутизации. Когда хуки не установлены, цена — одно сравнение с nil,
а поведение побайтово идентично апстриму.

Трассировка решения **продета сквозь настоящий код балансировщика**, а не переписана
рядом: `PickOutbound` вызывает `PickOutboundTraced` с nil-трассой, и каждый метод
трассировки безопасен к nil. Реализация каждого алгоритма балансировки ровно одна,
поэтому объяснение не может разойтись с поведением, которое объясняет. См.
[xray/README.md](xray/README.md).

**Сайдкар** линкует xray-core как библиотеку (для этой части форк не нужен) и подменяет
системный диалер через экспортированный и API-стабильный
`internet.UseAlternativeSystemDialer`.

**Инъекция сбоев ключуется по тегу outbound**, который читается из контекста дозвона. В
этом весь смысл: два outbound могут делить IP и порт сервера, и пакетный фильтр физически
не способен их различить — `pf` и `iptables` видят одинаковые 5-кортежи. Тег — способен.
`sidecar/e2e_test.go` доказывает ровно этот случай.

Сбои достоверны, потому что пробы обсерватории и пользовательский трафик идут по *одному
и тому же* пути дозвона, так что проверки здоровья видят отказ так же, как его видят
настоящие соединения, — и именно так ведёт себя белый список фаервола. Синтезированные
ошибки проверены на побайтовое совпадение с настоящими ошибками ядра
(`sidecar/fault/fault_test.go` сравнивает с реальным `ECONNREFUSED` от `127.0.0.1:1`), а
живые соединения тоже рвутся, потому что фаервол не ждёт вежливо, пока закончатся уже
открытые потоки.

### Чего эти сбои не могут

Указано и здесь, и в интерфейсе, потому что утверждение звучит как «будто по-настоящему
недоступен», а верно оно лишь по большей части:

1. Переходы `sockopt.dialerProxy` получают пайп от `redirect()` и до диалера не доходят.
2. Дозвоны внутреннего стека gVisor у WireGuard идут мимо; покрыт только внешний UDP.
3. Проверка `connectivity` у `burstObservatory` использует голый `http.Client` вне Xray.
4. Нет потери TCP-сегментов (из пользовательского пространства можно лишь тормозить или
   дёргать поток), нет ICMP, нет PMTUD.
5. Отказ DNS частичен — разрешение имени может произойти до того, как дело дойдёт до
   диалера.

## Лицензирование

Xray-core распространяется под **MPL-2.0**; патчи в `xray/patches/` — модификации файлов
под MPL-2.0 и остаются такими же.

Текст документации по параметрам в `data/docs-en/` и `data/docs-ru/` **адаптирован из
XTLS/Xray-docs-next и распространяется под CC BY-SA 4.0**. Поскольку это адаптированный
материал, к нему применяется ShareAlike — поэтому он лежит в отдельных каталогах со
своими `LICENSE` и `ATTRIBUTION.md`, и каждая подсказка ссылается на исходную страницу.
Это обязательство покрывает только извлечённый текст и не распространяется на код этого
проекта, который просто читает файл во время работы.

Собственные пояснения приложения — причины отсева, заметки о поведении, которого нет в
официальной документации, — намеренно держатся отдельно от извлечённого текста, чтобы
одно не приписывали другому.

## Упаковка

```bash
npm run package
```

```bash
npm run package:all          # все платформы одной командой
npm run package -- win       # или только одна: mac, win, linux
```

Обе сначала чистят `.build/dist/`. electron-builder перезаписывает то, что производит, но
никогда не удаляет то, что производить перестал, — без очистки устаревший артефакт от
прошлой версии лежал бы там с видом актуального и уехал бы в релиз вместе с остальными.

Скрипт проверяет запиненное ядро, гоняет тесты и **отказывается упаковывать, если они
падают**, собирает сайдкар под *каждую* цель — так поломка, специфичная для Windows,
всплывает на релизе с macOS, а не ждёт релиза с Windows, — собирает рендерер и пишет
установщики и архив исходников в `.build/dist/`.

Артефакты для macOS, Windows и Linux можно получить с Mac; CI всё равно собирает каждый
на своём раннере, потому что пользователи запустят именно AppImage, собранный на Linux, и
установщик, собранный на Windows.

Архив исходников делается через `git archive` на HEAD, а не из рабочего дерева. Значит,
в нём ровно отслеживаемые файлы — туда не могут попасть `node_modules`, пропатченное ядро
или артефакт прошлого релиза, — и если рабочее дерево разошлось с HEAD, скрипт об этом
скажет, потому что бинарники тогда собраны из чего-то, что архив не описывает. Бинарник
Go и сгенерированные бандлы `data/` едут как `extraResources` вне asar: сайдкар должен
быть настоящим файлом на диске, чтобы его можно было запустить, а файлы данных ищутся по
пути.

Иконка генерируется из `assets/icon.svg`:

```bash
npm run icon
```

Растеризация идёт через Chromium, а не через ImageMagick, который без делегата librsvg
молча выбрасывает каждую обводку — первая попытка вышла тремя точками, без единой
соединяющей линии и без предупреждения.

Тег `v*` запускает тот же скрипт в CI и прикладывает артефакты к **черновому**
пре-релизу, так что скачать ничего нельзя, пока на это не посмотрели.
